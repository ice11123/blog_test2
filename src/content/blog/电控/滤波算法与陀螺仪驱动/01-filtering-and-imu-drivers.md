这组资料覆盖三个层次：滤波算法、原始六轴传感器驱动，以及内部已经完成融合的姿态模块。它们解决的问题不同，不能只按“谁的角度更稳”进行比较。

```text
原始加速度/角速度
  → 标定与单位换算
  → 互补滤波、卡尔曼或 DMP
  → 姿态/状态估计
  → 控制器
```

只有最后一层进入实际控制，才算形成闭环。资料中没有提供统一硬件、测试日志和基准曲线，因此本文只确认原理与代码路径，不比较最终精度。

## `卡尔曼滤波融合.pdf`：多传感器状态估计设计

这份 13 页资料面向云台，把角度、角速度、角加速度和陀螺仪偏置组成四维状态，再融合编码器、IMU 与视觉测量。

### 预测与更新

预测步骤用上一时刻的状态和时间间隔推算当前状态，同时增加协方差，表示“时间越久，不确定性越大”。

更新步骤计算测量残差和卡尔曼增益。测量噪声较小时更相信传感器，过程噪声较大时更愿意跟随系统变化。

```text
预测：x⁻ = F·x + B·u
更新：x = x⁻ + K·(z - H·x⁻)
```

资料提出高频 IMU 每次到来都做预测，编码器和视觉按各自到达时间异步更新。这比强迫所有传感器使用同一频率更符合实际系统。

### 代码性质

PDF 给出 `KalmanFilter` 结构、4×4 协方差以及预测、编码器更新、IMU 更新等示例。它是一份设计稿和代码片段，不是可直接构建的完整库。

文中提到 100 Hz、STM32F4 和若干性能判断，但没有附测试工程、日志或测量方法。这些只能作为资料作者的设计说明，不能迁移成当前小车的实测结论。

## `卡尔曼滤波.zip`：角度与陀螺仪偏置的两状态实现

压缩包只有 `filter.c` 和 `filter.h`。代码分别为 X、Y 轴维护角度、偏置和 2×2 协方差，并提供一阶互补滤波作为轻量替代。

### 简化卡尔曼原理

陀螺仪负责短时间预测角度，加速度计角度负责纠正长期漂移。滤波器还估计一个陀螺仪偏置 `Q_bias`：

```c
angle += (gyro - bias) * dt;
error = accel_angle - angle;
angle += K0 * error;
bias  += K1 * error;
```

`Q_angle`、`Q_gyro` 和 `R_angle` 决定对模型与测量的信任程度。它们是噪声假设，不是越小越好。

### 互补滤波

同一文件还实现：

```c
angle = 0.02f * accel_angle
      + 0.98f * (angle + gyro * dt);
```

它用加速度计提供低频参考，用陀螺仪积分提供高频动态。计算量比卡尔曼小，但不能显式给出估计协方差。

### 代码边界

`dt` 固定为 5 ms，噪声参数也写死在函数内部。只要真实调用周期不是 5 ms，积分与协方差传播就会偏离设计。

X、Y 两个函数各自使用静态状态，不能为两块传感器创建多个实例，也不方便在模式切换时复位。要工程化，应把状态和参数放进结构体，并由调用者传入实际 `dt`。

## `MSPM0 编码器+6050+Pid.pdf`：平衡控制的数据链

这份 23 页资料把电机、编码器、MPU6050 和串级 PID 放在同一条平衡车链路中。

### 从传感器到执行器

代码示例先读取 MPU6050 和编码器，再计算直立环、速度环和转向环，最后叠加为两侧电机输出：

```text
姿态角 + 角速度 → 直立环 ┐
编码器速度       → 速度环 ├→ 左右 PWM → 电机
Z 轴角速度       → 转向环 ┘
```

直立环通常是响应最快的内环，速度环给它一个较慢的修正量。资料里的转向环示例暂时设为零，说明结构被预留，但当前片段没有启用完整转向控制。

### 驱动代码

PDF 展示了 MSPM0 GPIO 控制方向、定时器 PWM、编码器 GPIO 中断、I²C 寄存器读写和 MPU6050 数据换算。

I²C 示例大量使用等待状态寄存器的 `while`。资料没有超时和总线恢复逻辑，移植进协作式调度器前必须补上超时，否则断线或 NACK 可能让整车永久卡住。

### 文档边界

这是排版后的代码讲义，不包含可构建工程、活动 SysConfig 或硬件版本。引脚、PWM 范围和 PID 参数只能作为示例，不能据此给出接线或性能承诺。

## `6050-正点原子DMP库.zip`：寄存器驱动、DMP 文件与自定义 Roll 融合

压缩包含 MPU6050 寄存器驱动、InvenSense Motion Driver 文件、DMP 映射表，以及面向 MSPM0 的 I²C 适配和 `IMU.c`。

### 文件存在不等于 DMP 已接通

`inv_mpu.c` 与 `inv_mpu_dmp_motion_driver.c` 提供 DMP 固件、FIFO 和四元数接口，但 `IMU.c` 的当前输出路径没有调用 `dmp_read_fifo()`。

实际 `IMU_getEuleranAngles()` 读取原始六轴，只计算 Roll，并使用加速度角与 X 轴角速度做互补滤波。DMP 文件属于“仅发现文件”，不是已确认的运行链路。

### MPU6050 底层驱动

`bsp_mpu6050.c` 通过 MSPM0 DriverLib 完成寄存器收发，配置量程、采样率和低通滤波，并在 I²C 中断中维护收发状态。

所有等待循环都没有超时。I²C 设备缺失、总线忙或中断未到达时，函数可能一直不返回。

### `IMU.c` 的数学问题

`fast_sqrt()` 先用经典常数近似 `1/sqrt(x)`，最后却返回：

```c
return 1.0f / conv.f * x;
```

若 `conv.f ≈ 1/sqrt(x)`，该表达式约等于 `x·sqrt(x)`，不是 `sqrt(x)`。它会破坏向量和四元数归一化，必须改正并用已知输入做单元测试。

代码把陀螺仪换算为度每秒，却直接送入通常要求弧度每秒的四元数微分；更重要的是，该四元数结果没有参与最终 Roll 输出。当前可确认输出仍是独立互补滤波结果。

### 完整性问题

`bsp_mpu6050.c` 引用了压缩包中不存在的 `bsp_system.h`。`MPU6050_Init()` 的注释与实际返回值语义也相反。因此这是一组待移植源码，不是开箱即用的库。

## `jy901s库.zip`：11 字节串口帧状态机

压缩包包含 `jy901s.c`、`jy901s.h` 和 README，没有 CubeMX/Keil 工程或实际调用点。

### 接收与解析

驱动使用 UART 单字节中断接收。状态机依次等待 `0x55` 帧头、数据类型、8 字节数据和校验和，总帧长为 11 字节。

有效帧会按类型更新加速度、角速度或角度，并记录时间戳、包计数、错误计数和数据就绪标志。错误回调会重置解析器并重新启动接收。

```text
UART 字节 → 帧头同步 → 类型判断 → 数据收集
         → 累加校验 → 单位换算 → 数据有效标志
```

### 模块输出与本地校准

代码消费模块直接输出的角度帧，并按固定比例换算。姿态融合算法在模块内部，压缩包没有展示其实现。

本地自动校准在加速度和角度都曾有效后开始累加 100 次。但之后每收到任意类型帧都可能重复使用上一组加速度和角度，样本并不一定彼此独立。

它还把静止时 Z 轴重力一起平均为“零点偏移”。如果应用需要保留重力方向，这种处理会改变物理含义。校准必须区分传感器零偏、安装零位和重力分量。

### README 中不能直接采信的内容

README 列出数据频率、解析耗时、内存占用和丢包率，但包内没有测试工程、测量脚本或报告。代码中的 `JY901S_GetDataRate()` 实际计算的是“距离最近一帧的时间倒数”，也不是真正的滑动窗口频率。

这些性能数字应标为待验证。包内 README 声称 MIT，但压缩包没有附带 `LICENSE` 文件，公开复用前还要确认授权来源。

## `BNO080.zip`：STM32F103 上的 UART-RVC 示例

这是一个 STM32CubeMX/Keil 工程。配置确认 USART1 为 `115200、8N1`，RX 使用循环 DMA；`main()` 调用 `BNO080_Init()`，USART1 中断也实际调用了空闲帧处理函数。

因此它不同于只有驱动文件的资料：当前工程能追踪到完整的初始化和接收调用链，但仍没有本次环境中的编译与上板日志。

### RVC 数据路径

驱动启动 128 字节 DMA 接收并打开 UART IDLE 中断。出现空闲后停止 DMA、计算本次长度、扫描 19 字节 RVC 帧，校验通过后提取 yaw、pitch 和 roll。

```text
USART1 DMA → IDLE 中断 → 扫描 0xAA 0xAA
           → 校验和 → 三个 int16 → 角度 × 0.01
```

主循环复制共享结构，并通过 USART2 输出三轴角度。代码没有使用帧中携带的三轴线性加速度。

### 四个代码问题

1. `BNO080_GPIO_Config()` 先把 PB0 拉高，又把 PB0 拉低；第二次本应配置 PB1。该函数在 `main()` 中被注释，当前依赖外部硬件绑带选择模式。
2. 当 `data_length < 19` 时，扫描循环仍会执行一次，并可能解析缓冲区中的旧数据。
3. 帧头通过未对齐的 `uint16_t*` 强制转换读取，依赖小端和未对齐访问行为，逐字节比较更安全。
4. `BNO080_GetData()` 只复制结构。主循环清除的是本地副本的 `new_data_flag`，全局标志仍保持为 1，后续会把旧数据持续当作新数据打印。

这些问题不会否定 UART-RVC 的总体思路，但说明示例仍需要状态消费、短帧保护和解析测试后才能复用。

## `BNO080 Datasheet v1.3_1-49_翻译版.pdf`：协议真相源

提供的文件是 BNO080 数据手册 v1.3 的第 1–49 页节选。它覆盖架构、引脚、I²C、UART-SHTP、SPI、UART-RVC、传感器报告和坐标系，但不是原手册全部页数。

### UART-RVC 帧

手册第 20–21 页说明 UART-RVC 使用固定 `115200、8 数据位、1 停止位、无奇偶校验`。每帧 19 字节，包含：

```text
0xAA 0xAA | Index | Yaw | Pitch | Roll
          | X/Y/Z acceleration | Reserved | Checksum
```

三个角度都是小端 `int16`，分辨率为 `0.01°`。资料代码读取的偏移与这一帧表一致，但只消费了角度部分。

### 模式选择与坐标系

手册给出 PS0、PS1 模式选择和 UART-RVC 连接图。具体上拉、下拉和复位时序必须按实际模组原理图实施，不能只靠示例工程中的 GPIO 注释接线。

手册还定义了器件坐标系和旋转报告。把 yaw、pitch、roll 送入车辆控制前，必须明确模块安装方向、车体坐标和正方向，否则“数值正常”仍可能产生相反控制。

## 四类方案怎么选

| 方案 | 主控拿到什么 | 主控工作量 | 当前资料状态 |
| --- | --- | --- | --- |
| MPU6050 原始驱动 | 加速度与角速度 | 自己标定、融合 | 有源码，集成不完整 |
| `filter.c` | 角度与偏置估计 | 需要提供角度测量和固定周期 | 两状态实现存在 |
| JY901S | 模块输出的加速度、角速度、角度帧 | 解析、校准和状态管理 | 只有驱动文件 |
| BNO080 UART-RVC | 已融合角度与线性加速度帧 | DMA、帧解析和坐标映射 | 工程调用链存在 |

## 本篇总结

- 滤波器必须与真实采样周期、噪声和坐标系一起设计。
- MPU6050 提供原始六轴，DMP 文件存在不代表程序已经使用 DMP。
- JY901S 和 BNO080 示例主要解决串口帧解析，模块内部融合算法不在代码包中。
- BNO080 工程调用链最完整，但新数据消费、短帧和模式 GPIO 仍有明确缺陷。
- 下一步应先建立原始数据、时间戳、丢包率和静态漂移记录，再谈滤波参数和控制性能。
