资料名里带有“RTOS”，但源码和 README 都明确说明：它是裸机协作式周期调度器，不是 FreeRTOS，也没有任务栈、上下文切换或抢占。

它的价值在于把一个不断膨胀的 `while (1)` 拆成多个周期任务。它的限制也很明确：任何任务阻塞，整个系统都会被一起拖慢。

## `非抢占式任务调度器_Cooperative_Scheduler.zip`

压缩包只包含 `Task.c/.h`、`SysTick.c/.h` 和 `README.md`。与同目录下已解压文件逐一计算 SHA-256 后，五个文件完全一致，因此它们是同一份资料的两种保存形式，不是两个版本。

### 调度模型

主循环持续调用 `Task_Start()`：

```c
while (1) {
    Task_Start(Sys_GetTick);
}
```

每个任务保存上次运行时刻和周期。满足下面的条件时，调度器直接调用函数指针：

```c
if (now - task->LastWakeUp >= task->Interval) {
    task->Function(task->Para);
}
```

无符号减法可以自然处理 32 位 tick 回绕。任务执行完后，`LastWakeUp` 按周期递增；如果已经落后超过一个周期，则直接追到当前时刻，避免短时间连续补跑很多次。

### 优先级的真实含义

`Task_Add()` 使用 `qsort()` 按优先级和创建顺序排列任务表。优先级数值越小，遍历位置越靠前。

这里的优先级只决定“多个任务同时到期时先调用谁”。低优先级任务开始运行后，高优先级任务不能中途打断它，因此它不是实时系统中的抢占优先级。

### 任务生命周期

调度器提供暂停、恢复和删除接口：

```c
Task_Suspend("OLED");
Task_Resume("OLED");
Task_Delete("OLED");
```

删除只是把状态改为 `INACTIVE`，不会压缩任务表，也不会减少 `Task_Num`。达到 `MAXTASKS` 后，即使删除旧任务，也不能再添加新任务。

## 已解压目录：`Task.c`、`Task.h`、`SysTick.c` 与 `SysTick.h`

### 1 ms 时基

`SysTick_Increasment()` 递增 `uwTick`，并让 `delayTick` 递减。`Sys_GetTick()` 把当前毫秒 tick 返回给调度器。

```c
void SysTick_Increasment(void)
{
    uwTick++;
    if (delayTick) delayTick--;
}
```

源码没有展示中断向量和 SysConfig，因此只能确认时基函数存在，不能仅凭这五个文件确认它已被某个具体工程的 SysTick 中断调用。

### 阻塞延时与协作式调度冲突

`Delay()` 会在 `while (delayTick)` 中等待。若任务函数内部调用它，主循环就无法返回 `Task_Start()`，其他任务也无法获得执行机会。

协作式任务应该把“等待”改为状态和时间戳：当前调用只推进一步，下一次周期到达后再继续，而不是占住 CPU 等待条件成立。

### 推荐的任务形状

```c
void EncoderTask(void *context)
{
    EncoderSample *sample = context;
    sample->count = Encoder_ReadAndClear();
}
```

任务应完成一次短操作后立即返回。编码器采样、PID、循迹可以高频运行；OLED 和串口输出应降低频率，并限制单次输出量。

## 代码审查：当前实现的四个关键问题

### 任务名使用指针比较

暂停、恢复、删除和查询函数使用：

```c
if (Task_Schedule[i].Name == taskName)
```

这比较的是两个字符串指针是否指向同一地址，而不是文字是否相同。传入同一个字符串常量时可能看似正常，但动态字符串或不同编译单元不可靠。

正确方向是使用 `strcmp()`，或让注册接口返回稳定的任务句柄，后续管理不再依赖名字查找。

### `MaxUsed` 没有保存最大值

每次任务结束后，代码直接执行：

```c
Task_Schedule[i].MaxUsed = TickDiff;
```

因此字段记录的是“最近一次耗时”，而不是注释所说的“最大耗时”。应只在 `TickDiff > MaxUsed` 时更新，并另外保存最近值，避免一个字段承担两种语义。

### 空闲函数调用时机不准确

`Task_IdleFunction()` 位于任务遍历的 `else` 分支。只要当前检查的某个任务尚未到期，它就会被调用一次，即使本轮其他任务刚刚运行过。

真正的系统空闲应在完整遍历结束后，根据“本轮没有执行任何任务”统一判断。否则低功耗、后台统计或喂狗逻辑可能重复触发。

### 两个关闭的实验分支仍有逻辑问题

`DYNAMIC_MODIFY` 默认是 `0`。其最小周期变量从 `0` 开始，更新表达式无法把它变成首个任务周期，因此启用后动态调整依据会失真。

`LOW_POWER` 默认也是 `0`。状态枚举中 `SCHEDULE_IDLE` 为 `0`、`SCHEDULE_BUSY` 为 `1`，但低功耗条件直接测试 `All_Scheduler_IDLE`，反而会在忙状态为真。

这两个问题目前不会进入编译后的执行路径，但在打开宏之前必须修复，不能因为默认关闭就把它们视作已完成能力。

## 调度器适合什么场景

| 场景 | 适合程度 | 原因 |
| --- | --- | --- |
| 小车周期采样与控制 | 适合 | 任务短、周期清晰、资源有限 |
| 大量阻塞式通信 | 不适合 | 一个任务会拖慢全部任务 |
| 需要硬实时抢占 | 不适合 | 没有上下文切换与抢占 |
| 教学和小型裸机项目 | 适合 | 执行路径直观、调试成本低 |

## 本篇总结

- 这是一套协作式周期调度器，不是完整 RTOS。
- 每个任务都必须短小、可返回，阻塞延时会阻塞整个系统。
- 优先级只决定同时到期时的先后顺序，不能打断正在运行的任务。
- 任务名比较、耗时统计、空闲调用和关闭分支需要修正后再作为公共组件使用。
- 真正的可靠性来自周期抖动、最坏执行时间和超时路径的上板测量，而不是任务表看起来整齐。
