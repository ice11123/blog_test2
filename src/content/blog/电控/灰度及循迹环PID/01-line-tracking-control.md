循迹控制不是“看到黑线就转弯”这么简单。完整链路需要把离散传感器状态转换成连续位置误差，再由方向环生成左右轮差速，最后交给电机驱动执行。

本目录有一份独立 `Tracker.c` 和一个完整压缩工程。两者采用不同的位置表示法，而且独立文件明确标注“备用未调用”，不能混写成同一条运行链路。

> [!IMPORTANT]
> 原始包名与 SysConfig 记录了具体器件。为与本站专题保持一致，正文统一使用 `MSPM0G35XX`；涉及证据时保留原始文件名。供电、电平、灰度模块输出极性和电机额定值仍应以实际硬件资料为准。

## `Tracker.c`：八路数字传感器的加权位置

### 原理

八个 GPIO 先被归一化为 `0/1`。代码把左侧三路映射为 `-3、-2、-1`，中间两路映射为 `0`，右侧三路映射为 `1、2、3`。

若同时检测到多路信号，就取所有有效传感器位置的平均值：

```text
offset = Σ(active[i] × position[i]) / Σactive[i]
```

这种质心法比“只取最左或最右一路”更连续。压在线宽较大的黑线上时，多路同时触发仍能给出中间位置。

### 代码接口

```c
bool Tracker_Read(uint8_t *states, _iq *offset);
```

函数检查空指针，读取八路 GPIO，并通过 `_IQdiv()` 计算定点偏差。没有任何传感器有效时返回 `false`，调用方需要决定保持旧方向、减速搜索还是安全停车。

### 当前文件的边界

文件第一行注释明确说明：底层逻辑已经直接写进 `task_app.c`，本文件备用且未调用。因此这里只能确认算法实现存在，不能说它进入了当前车辆控制链。

`DIS_INRERVAL` 定义为 `_IQ(1.5)`，旁边注释却写“1.0 cm”，而且实际位置计算没有使用该宏。偏差现在是传感器索引单位，不是经过标定的厘米值。

## `MSPM0G3507_Project_xunji_pid.zip`：十二路循迹工程

### 工程包含什么

压缩包包含 SysConfig、Keil 工程、生成代码和构建产物。自研逻辑集中在：

| 模块 | 关键文件 | 作用 |
| --- | --- | --- |
| 主流程 | `empty.c` | 初始化、按键、OLED、定时中断和模式开关 |
| 循迹 | `BSP/XUNJI/xunji.c` | 读取十二路 GPIO 并计算位置 |
| 控制 | `BSP/PID/pid.c` | 速度、循迹位置和角度 PID |
| 电机 | `BSP/MOTER/moter.c` | 方向 GPIO 与四路 PWM |
| 编码器 | `BSP/ENCODER/encoder.c` | A 相中断计数，B 相判断方向 |

`empty.syscfg` 确认配置了十二路循迹 GPIO、四路 PWM、左右编码器输入、UART、SysTick 和一个 50 ms 周期定时器。配置存在不等于硬件已经接好，但能证明代码预期的资源关系。

### 十二路位置估计

`xunji_shua_xin()` 依次读取 `L6…L1、R1…R6`，把有效通道映射为 `1…12`，再求平均：

```c
xun = (l6*1 + l5*2 + ... + r5*11 + r6*12) / active_count;
```

中线位于 `6.5`。方向环使用：

```c
steer = place_PID_value(6.5f, xun);
left_pwm  = 300 - steer;
right_pwm = 300 + steer;
```

误差为零时左右轮获得同样的基础输出；线向一侧偏移时，PID 输出以相反方向叠加到两侧轮，形成差速转向。

### 实际运行链路

`main()` 初始化板级配置、OLED 和控制定时器，然后把四路 PWM 清零。按键切换 `jb`；当 `jb == 1` 时，50 ms 定时器中断执行：

```text
读取十二路灰度
  → 计算 xun
  → 方向位置 PID
  → 基础 PWM ± 转向量
  → Set_Pwm()
```

编码器在 GPIO 中断中累加。SysTick 每约 10 ms 读取并清零计数，再用 `0.3 × 新值 + 0.7 × 旧值` 做低通。

不过速度 PID 的调用在控制中断里被注释掉。当前可达控制路径是开环基础 PWM 加循迹方向环，不能称为已启用的双轮速度闭环。

### 电机执行

`Set_Pwm()` 根据四个输入的正负切换左右方向 GPIO，再把绝对值写入四个定时器比较寄存器。

代码没有在函数内部执行 PWM 限幅，主流程里原有的上下限处理也被注释。方向环输出较大时，比较值可能超过预期范围；具体安全上限必须从计数周期、电机驱动和供电条件确定。

### 编码器反馈

左右编码器都在 A 相上升沿触发中断，再读取 B 相电平判断方向。这是单边沿正交解码，计数倍率低于双边沿或完整四倍频，但中断负担也更小。

资料没有轮径、减速比和每圈脉冲数，所以当前计数只能解释为固定窗口内的脉冲变化，不能直接写成 RPM 或厘米每秒。

## 代码审查：不能忽略的失线与实时性问题

### 失线逻辑互相抵消

`xunji_shua_xin()` 在没有任何有效通道时把 `xun` 恢复成 `last_xun`。随后控制中断又尝试用 `if (xun == 0)` 停车。

由于 `last_xun` 初始为 `6.5`，失线后 `xun` 通常不会是零，停车条件也就不会成立。应单独返回 `line_detected`，不要用一个位置数值同时表示“线的位置”和“是否看见线”。

### 标志函数的注释与返回值相反

`xunji_biao_zhi()` 的注释写“有黑带返回 1”，代码却在任一路有效时返回 `0`，全白时返回 `1`。调用前必须统一语义，否则状态机会把赛道和失线判断颠倒。

### 中断里执行了完整浮点控制

50 ms 定时器中断包含十二路 GPIO 读取、浮点平均、PID 和 PWM 更新。当前规模可能能运行，但中断执行时间没有测量；如果后续加入串口、OLED 或更多算法，会增加其他中断延迟。

更稳妥的结构是让中断只设置任务标志，控制计算放到主循环调度器中，并记录开始、结束 tick 或周期抖动。

### 代码包混有生成物

压缩包同时包含 `.o`、`.d`、映射文件和 J-Link 日志。接手时应从 SysConfig、工程配置和源码重新构建，不要把旧目标文件当成当前源码已经成功编译的证据。

## 两种循迹实现的区别

| 对比项 | `Tracker.c` | 压缩工程 `xunji.c` |
| --- | --- | --- |
| 通道数 | 8 | 12 |
| 位置坐标 | `-3…3`，中间两路为 0 | `1…12`，中心为 6.5 |
| 无线处理 | 返回 `false` | 保持上次位置 |
| 数值类型 | `_iq` 定点 | `float` |
| 是否进入工程调用链 | 注释明确未调用 | 控制定时器中实际调用 |

## 本篇总结

- 循迹系统要先把离散传感器状态转换为连续位置误差，再由方向环产生左右轮差速。
- `Tracker.c` 是未调用的备用八路实现；当前压缩工程实际使用十二路 `xunji.c`。
- 当前可达路径启用了方向环，但速度环调用仍被注释。
- 失线状态必须与位置数值分开表达，不能依赖 `xun == 0`。
- PWM 上限、传感器极性、物理间距和编码器换算都需要结合实物重新标定。
