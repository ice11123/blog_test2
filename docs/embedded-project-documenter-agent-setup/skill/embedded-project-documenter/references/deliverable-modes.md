# 交付模式

## 新生教程

目标是让读者安全地获得一个可观察结果，并理解最小因果链。

推荐结构：

1. 本篇目标与最终现象
2. 开始前需要具备什么
3. 硬件/软件安全检查
4. 一个核心概念
5. 最小实验步骤
6. 关键代码路径解读
7. 预期现象
8. 按症状排错
9. 本篇总结

系列文章按“可观察能力”拆分，而不是按源码目录拆分。例如先完成下载与日志，再完成单个传感器读取，再完成电机开环，最后进入闭环控制。每篇只引入支撑本篇现象的架构信息。

## 作品或项目介绍

目标是让外部读者快速理解作品做什么、为什么可信、边界在哪里。

推荐结构：

1. 问题与使用场景
2. 作品能做什么
3. 已确认的硬件组成
4. 数据流与控制流
5. 关键技术选择及理由
6. 演示或测量证据
7. 当前限制与下一步

不把编译通过当作作品性能证据。没有视频、日志或测量值时，把能力表述为“代码实现/设计目标”，而非“已经达到”。

## 工程技术参考

目标是支持接手、复现、维护和排障。

推荐结构：

1. 适用硬件版本与工具链版本
2. 仓库边界和生成代码边界
3. 活动构建配置与构建命令
4. 启动链路、任务/中断与调用关系
5. 外设、引脚、总线和资源映射
6. 数据结构、状态机和控制周期
7. 日志、断点、测量点与常见故障
8. 已验证事实、待验证项和已知限制

## 受众校准

- 新生：解释“为什么能看到这个现象”，少用缩写，避免一次展示全工程。
- 有基础成员：突出模块边界、数据流、修改点和调试方法。
- 维护者：突出版本、配置、依赖、真相源、失败恢复和变更影响。
- 展示/招生读者：突出目标、可验证成果和团队能力，但不省略关键限制。

同一份材料不要同时承担教程、宣传页和维护手册三种职责；需要时产出互相链接的三份文档。
