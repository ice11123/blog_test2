## 核心判断

“混乱”不能直接归因于动画多。本轮截图里本站并未出现立绘压住标题或正文的明显碰撞；三层波浪也不是卡片信息难读的主因。更值得调整的是内容密度、装饰风格一致性，以及主题入口和近期文章入口之间的关系。

两站首页承担不同任务：参考站展示 4 篇文章，每张卡回答“读哪一篇”；本站展示知识主题，每张卡同时回答“进哪个分类”和“读哪篇最近文章”。把本站直接变成参考站的交错文章卡，会丢掉主题导航的价值。应借鉴它明确的图文边界和稳定的内容顺序，保留本站主题组织。

## 已观察事实

参考站桌面卡片在同一列表里交替图片左右位置，图片使用清晰的斜边裁切，正文在独立白底区域，视觉顺序稳定为元数据、标题、摘要、标签。移动截图变成图片上置、文字下置。图像鲜艳但没有与正文叠放争夺阅读区。也不是所有细节都值得复制：移动长标题出现省略，右侧浮动工具覆盖部分卡边，more 按钮伸出卡角。这些只是可见设计选择，并不等于本站该采用相同行为。

本站桌面主题卡使用不等宽两列，AI 卡是符号、电控是真实模型抠图、学习笔记是线描书本、电源是线描电路。当前文字安全区已经存在，近期文章横跨卡下半区；不可误报为“没有预留立绘区”。移动卡片上半区明显高于实际文字需要，0 篇电源卡也保留大块空间；英文眉题显示为 `POWER ELECTRO...`、`FOUNDATION NO...`，下方再重复 `RECENT SIGNALS`。中文主题名清楚，但辅助装饰标签频繁截断，造成模板感。

本站桌面首屏侧栏头像、站名、简介、社交、计数和导航连续占据较大纵向空间；页头重复站名、社交和导航。重复不等于错误，但主页阅读重心在头图与卡片之间移动时，两套同级导航增加静态存在感。

## 卡片与标签：源码能证明什么

`src/components/home/TopicAtlas.astro:103` 的 `.topic-card-link` 是分类真实链接；近期文章行另有 `blogPostPath(post.id)` 链接。`.topic-copy` 处于更高层并设置 pointer-events；这说明实现区分了卡片与条目，但不证明实际命中、焦点与悬停体验正确。

`TopicAtlas.astro:294` 附近 `.topic-intro` 预留桌面 170px，上限 900px 时改为 180px；680px 移动规则未重设这一高度。因此移动可见的大留白与样式相符。默认宽度为 64% / 紧凑卡 61%，移动为 63%，装饰约 30%，这也支持“已划分安全区”的判断。

`TopicAtlas.astro:607` 附近 hover 使用 `(hover: hover) and (pointer: fine)`，存在轻微 3D 位移；还有 active 和 reduced-motion 分支。不能机械照技能清单说“缺少触控 hover 限制”“没有按压反馈”。这些基础已经做了；实际动效平滑、可中断和低性能设备表现仍未验证。

`src/components/layout/PersistentSidebar.astro:55` 起三个按钮有 tab 角色、aria-selected、aria-controls 和 tabindex；`src/scripts/persistent-sidebar.ts` 有箭头/Home/End 导航，键盘切换不会触发鼠标使用的 160ms 面板动画。源码设计符合高频键盘操作应即时响应的原则。

`PersistentSidebar.astro:149` 起真实存在标签筛选输入、状态计数和真实链接；标签 href 使用 `/blog/tag/${encodeURIComponent(tag.name)}/` 并由 withBase 添加基路径。脚本 input 事件调用 matchesTagFilter，更新 hidden 和“没有匹配的标签”。因此不能把当前版本批评成“标签不可用/只有装饰/尚无筛选”。

只读 DOM 中观察到参考站 `/tags/nas`、`/tags/ai` 等真实 href；本站 `/blog_test2/blog/tag/Markdown/`、`/blog_test2/blog/tag/Windows/` 等真实 href。它们是链接存在的证据，**不是已点击并成功到达结果页的证据**。本站标签目录页文件是 `src/pages/blog/tags.astro`，详情页是 `src/pages/blog/tag/[tag].astro`。

参考仓库 README 确认主题提供分类、标签、静态搜索等功能，但 README 宣称不能代替本轮线上操作。仅阅读与借鉴设计方法，没有复制 AGPL 源码。

## 未验证项与补验标准

卡片 hover、按下、点击分类、点击近期文章、键盘焦点是否分别清楚；标签页打开、输入筛选、空结果、清空恢复、点击标签后 URL/标题/数量一致；左栏三 tabs 的视觉切换与页面间持久状态；文章 TOC 的位置/当前高亮/滚动落点；搜索打开、输入、结果跳转、Escape；主题圆形切换及壁纸抽屉打开关闭；移动实际触摸和回退恢复。本轮这些均未完成。

后续应以“从主题进入分类→进入文章→TOC跳转→返回→标签筛选→点击标签”作为连贯路径验收，而非只证明每个按钮有事件。每段记录起止 URL、可见状态与截图；截图/浏览器恢复前，本报告只能作为有依据的设计方向，不能作为全面交互审查完成证明。

## 补充：参考站互动源码与可迁移规则

以下四个文件于本轮通过 web 实际读取，均来自参考仓库可变的 main 分支，不代表已证明线上部署使用完全相同版本。只做结构解读，不复制代码；所有互动仍属线上未验。

**文章卡。** [PostItemCard.astro](https://raw.githubusercontent.com/Symb0x76/astro-koharu/main/src/components/post/PostItemCard.astro) 将封面、标题和 more 指向文章，分类与标签有各自独立链接。容器 hover 改阴影，封面随 group hover 放大旋转。值得借鉴的是“一张视觉卡片容纳明确分工的链接”，而非把卡内所有内容都变成同一目的地。该文件还使用 500ms 图片过渡以及 more 按钮的 transition-all；它们不是高性能保证，不应照搬到本站高频浏览反馈。本站已有更短过渡和触控条件，应先体验再判断是否需要改动。

**标签页。** [tags/index.astro](https://raw.githubusercontent.com/Symb0x76/astro-koharu/main/src/pages/tags/index.astro) 按使用次数排序，次数大于 1 的标签直接展示，只出现 1 次的交给折叠区。这不是随机标签云，而是用内容频率分配首屏注意力。值得借鉴“常用先见、长尾可达”，不应不加检验地沿用大于 1 的阈值；本站 151 个标签的实际分布决定默认展开多少。

**折叠行为。** [CollapsibleTags.tsx](https://raw.githubusercontent.com/Symb0x76/astro-koharu/main/src/components/tag/CollapsibleTags.tsx) 使用独立按钮、数量、箭头旋转及 aria-expanded/aria-controls 表达展开状态。内容区使用 300ms grid-template-rows 变化。可借鉴的是状态清楚、动作命名与剩余数量可见；布局属性动画会产生布局工作，不能宣传成纯合成层或无成本动画。源码未在该文件显示完整的折叠焦点管理、减少动效处理，不能据此认证其无障碍完成。

**侧栏分段。** [HomeSiderSegmented.tsx](https://raw.githubusercontent.com/Symb0x76/astro-koharu/main/src/components/ui/segmented/HomeSiderSegmented.tsx) 的三项语义为概览、本文目录、系列，并通过状态存储切换。本站确认的是个人、全站目录、标签，右侧另有本文 TOC。这两种信息架构不同。借鉴紧凑分段的选中反馈即可，不能为了“像参考站”把本站全站目录替换成本文目录，或将用户确认的标签项换成系列。

## 补充：标签页主内容的明确方案

左栏标签筛选解决“已知名称，快速找到”；独立标签总览还应解决“我不知道搜什么，先看看本站写了哪些主题”。151 个标签并不意味着只能做筛选列表，发现与检索可以共存。

建议标签总览保留真实标签 URL，主标题下显示总标签数，再安排一个简洁筛选框。无查询时，先展示有多篇文章的常用标签，按实际篇数排序；单篇长尾用“更多标签 · N”渐进展开，并保留直接查看全部的入口。有查询时必须对全部标签匹配，不能只查当前展开区域；反馈匹配数量和清空入口。每个标签仍显示名称与篇数，不新增随机大小或多套颜色。阈值与默认数量应先检查分布，避免常用区自身又变成很长的标签墙。

标签详情页则明确展示“标签名称 / N 篇文章 / 返回全部标签”，下方保持文章列表。回退时是否保留查询和展开状态必须实测，不在此假定已实现。标签筛选是页面内工具，不应把标签真实链接替换成只有 JavaScript 才能使用的按钮。

| Before | After | Why |
| --- | --- | --- |
| 本站 tags.astro 把全部标签按次数排序后平铺，主内容缺少发现与检索的分工 | 常用标签先展示、长尾可展开、查询覆盖全部，保留全部入口和现有 URL | 将频率用作渐进披露，既支持探索也支持精确寻找，不靠缩小字号塞下 151 个标签 |
| tags.astro 与 tag/[tag].astro 向公共内容布局传入 new Date() | 聚合页标题区不显示文章式发布日期；若需要“最后更新”，以明确内容数据计算并正确命名 | 构建时间不能冒充标签或文章发布时间，聚合页首先应回答范围与数量 |

后一项来自本地源码核查：两个标签页面均使用 PublicContentLayout，并传入 pubDate={new Date()}。`PublicContentLayout.astro:28` 的 showDate 默认 true，39—40 行据此渲染日期，两个调用处均未关闭；因此静态构建会将构建时日期放入标题区。线上截图尚未取得，不能把源码推导写成已亲眼看见的线上错误。
